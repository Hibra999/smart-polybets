Sports Quant Trading System

Hedge fund sintético asistido por Claude · Polymarket‑first, deportes como plugins · repo: pypro_polymarket_agent

Idea central. Claude opera como analista cuantitativo, gestor de riesgo y operador; el humano es el CIO que aprueba lo ambiguo y delega lo obvio. Principio rector: reproducibilidad hacia adelante — cada decisión es determinística: inputs documentados → funciones puras versionadas con contratos Pydantic. Polymarket es el mercado principal y se accede por un único gateway sobre una sola librería (el SDK oficial); los deportes se “pegan” encima como proveedores de señal.

4 · Interacción con Polymarket — un gateway, una librería

Antes: dos clientes (scraper requests a Gamma + SDK). Ahora: un gateway (venue/) sobre el SDK oficial (PublicClient + SecureClient). El scraper de Gamma fue retirado. Los Protocols (MarketSource, AccountSource) se conservan como interfaz; los adapters delegan en el gateway.

Descubrimiento

PublicClient (sin auth)
  • find_match_markets(home, away) vía list_events/search + matching por nombre.
  • best_ask, order book, precios, sports, tags.

Cuenta

SecureClient (auth)
  • balance, positions (mark-to-market), open_orders, closed_positions.

Ejecución

SecureClient (auth)
  • place(TradeOrder), cancel(order_id) — dry-run por defecto, con los gates.

Fábrica única del cliente + lección de naming

core/polymarket_client.build_secure_client() es el único lugar que construye el SecureClient. El área se llama venue/ a propósito: nombrarla polymarket/ hacía sombra al import del SDK y rompía el path live (los tests pasaban por usar fakes) — regla: nunca nombrar un módulo propio igual que una dependencia.

8 · Refactor Polymarket-first — hoja de ruta

Fase 1 — Gateway único + retirar Gamma en curso/hecho

Crear venue/PolymarketGateway sobre el SDK; adapters delegan; se retira el scraper Gamma. Una sola librería.

Fase 2 — Un estado + consolidar scripts planeado

Retirar el backend Django (django_client, django_sync_tools); quedan place_bets/orders/account/suggestions.

Fase 3 — Deportes como plugins planeado

SignalProvider por deporte: dado un mercado de Polymarket → probabilidad/edge. Pegar un deporte = registrar un provider, no un pipeline. Entrypoint mercado → señal → decidir → ejecutar.

9 · Reglas de oro (anti-deuda)

  • Schemas inmutables (v2, no in-place).
  • Funciones puras: estado/API en tools o core, no en functions.
  • STRATEGY.md única fuente de reglas.
  • Idempotency key en todo.
  • Todo lo generado lleva generated_at/tournament_id/strategy_version.
  • Estado siempre fresco; una sola librería de venue.
