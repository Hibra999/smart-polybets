Validaciones mandatorias de dependencias

Sistema de precondiciones + hooks · Sports Quant Trading · referencia de operación

Estado: diseño aprobado — implementación pendiente. Este documento describe cómo funciona (y funcionará) el sistema de validaciones. Diseño completo: docs/superpowers/specs/2026-07-17-mandatory-dependency-hooks-design.md.

Por qué existe

Los modelos reproducen los fixtures jugados en runtime: si la base de datos del torneo está desactualizada, los edges son falsos y el PnL/las sugerencias engañan. Antes, "refrescar datos antes de sugerir o apostar" vivía solo como prosa en el protocolo — fácil de olvidar. Ahora es una validación enforced: el sistema detecta datos viejos y bloquea o avisa según lo que estés por hacer.

Qué se valida (precondiciones)

PrecondiciónSeveridadQué verificaCómo lo arreglás
fixtures_finalized mandatory No hay partidos ya jugados sin finalizar en la DB (kickoff pasado + status scheduled, excluyendo los que están en juego ahora). python scripts/update_results.py --tournament <tid> --apply
live_gates_ready mandatory (solo dinero) Están la private key, POLYMARKET_LIVE=1 y el kill-switch apagado. Setear el entorno / desactivar el kill-switch.
placeholders_synced advisory Los placeholders de bracket con mercado abierto ya están mapeados a equipos reales. Requiere red → puede quedar "no verificable". python scripts/sync_upcoming_fixtures.py --apply (WC)
fetch_fixtures_pm.py --apply (Liga MX)

La verificación es multi-torneo: recorre los torneos activos del registry (por ventana de fechas) y corre las precondiciones locales sobre cada base de datos.

Qué pasa cuando algo falla (por nivel de acción)

AcciónNivelSi una dependencia no se cumple
account.py (PnL), scan_market.pylectura / análisis AVISA imprime la violación + el comando de remedio, y continúa.
propose_bet.py, place_bets.py, orders.pydinero BLOQUEA se rechaza hasta refrescar, o forzás con --force --reason "…" (queda registrado).

Una acción de dinero sobre un mercado concreto bloquea solo si su torneo está viejo — no te frena una apuesta de Liga MX porque el Mundial quedó sin actualizar.

Cómo se usa

Verificar el estado en cualquier momento

python scripts/check_freshness.py          # resumen legible
python scripts/check_freshness.py --json   # para scripts/cron
# exit code != 0 si hay alguna violación mandatoria

Al arrancar una sesión de Claude Code

Un hook SessionStart (en .claude/settings.json) corre esa verificación automáticamente y te inyecta el estado al contexto. Cada sesión arranca sabiendo si hay datos viejos — exactamente lo que faltó el día que el PnL salió mal.

Si una acción de dinero te bloquea

# 1. refrescá lo que el mensaje te indique, p.ej.:
python scripts/update_results.py --tournament fifa_world_cup_2026 --apply
# 2. reintentá la acción; o, si sabés lo que hacés:
python scripts/propose_bet.py ... --force --reason "dato al día verificado a mano"

Cómo encaja (arquitectura)

Fuente de verdad: core/preconditions.py — predicados puros + evaluate(tier, tournaments). Testeable, determinístico, sin efectos.
Capa 1 · guards: una línea enforce(tier, …) al inicio de cada acción → bloquea o avisa.
Capa 2 · CLI: scripts/check_freshness.py → texto/JSON + exit code.
Capa 3 · hook: SessionStart inyecta el estado al agente.

Las tres capas cuelgan del mismo módulo puro: un solo lugar define "qué está fresco", un solo formato de mensaje.
